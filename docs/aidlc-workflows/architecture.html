AIDLC-WORKFLOWS / ARCHITECTURE

リポジトリ構成　1 つの core を 5 つのハーネスへ投影する

設計の柱は「手書きの正は 1 箇所、配布物はすべて生成」。core/ にあるステージ、エージェント、フック、ツールは、scripts/package.ts が dist/<name>/ へ投影する。投影の指示は harness/<name>/manifest.ts の宣言が与える。生成物は git にコミットされ、--check がバイト単位の差分でドリフトを封じる。エンジンの TypeScript は 5 ハーネスでバイト同一。

リポジトリマップ

トップレベルは 7 区画で、生成物は dist だけである。手書きは core / harness / plugins / docs / tests / scripts の 6 つになる。core の内訳は Markdown 16,610 行と TypeScript 41,958 行で、前者が方法論、ペルソナ、ナレッジ、後者がエンジン、フック、センサーを担う。「知識は Markdown、機構は TypeScript」の分離が、ファイル種別のレベルで貫かれている。

core/ # 手書きの正（ハーネス非依存） ├── aidlc-common/ # conductor.md + protocols 4 + stages 32（5 フェーズ） ├── agents/ # 14 エージェント .md（frontmatter に tier:） ├── hooks/ # 14 フック .ts（ハーネスイベント → エンジン） ├── tools/ # 32 ツール .ts（orchestrate / state / swarm / sensor …） ├── knowledge/ # 59 ナレッジ .md（エージェント別 + aidlc-shared） ├── scopes/ sensors/ memory/ # 9 スコープ / 5 センサー / ルール雛形 └── skills/ templates/ # セッションスキル 3 + onboarding 雛形 harness/ # ハーネス別オーバーレイ × 5（claude / codex / kiro / kiro-ide / opencode） │ # manifest.ts（投影レシピ）+ adapter + 認可済み設定 dist/ # 生成物（コミット済み）: ハーネス 5 + plugins plugins/ # サンプルプラグイン test-pro（stages / sensors / agents を寄与） scripts/ # package.ts（パッケージャ）/ manifest-types.ts / onboarding.ts docs/ # 公式ドキュメント 91 md（guide / harness-engineering / reference） tests/ # 356 テストファイル（smoke / unit / integration / e2e + 独自駆動基盤）
参照: core/ harness/ dist/

パッケージングパイプライン　buildTree() の 8 手

bun scripts/package.ts が全ハーネスを再生成する。ハーネスは manifest.ts を持つディレクトリの走査で見つかるので、パッケージャにハーネス名のハードコードはない。ハーネスごとの組み立て（buildTree）は次の 8 手で進む。

  1. core の各ディレクトリを変換しつつ <harnessDir>/ へコピーし、続いてオーバーレイの authored ファイルをコピーする。
  2. onboarding 雛形から CLAUDE.md / AGENTS.md を描画し、aidlc/ ワークスペース雛形と memory-seed を配置する。
  3. 組み上がったツリー内で aidlc-graph.ts compile を実行し、stage-graph.json と scope-grid.json を生成する。
  4. rules ディレクトリ名を実行時に解決するための harness.json を出力し、ステージ、スコープごとのスキルランナーを生成して、任意の emit() プラグインを呼ぶ。

変換は 1 クラスしかない。対象は .md のみで、.ts と .json は無変換でコピーされる。エンジンがハーネス間でバイト同一なのはこのためである。.md に走る書き換えは 4 つある。レビュアーのナレッジ吸収、{{HARNESS_DIR}} トークンの置換（.claude / .kiro / .codex / .aidlc）、rules ディレクトリ名の文中リネーム、エージェント frontmatter の tier 投影である。

参照: scripts/package.ts（buildTree 全体） docs/harness-engineering/00-overview.md

manifest 契約　ハーネスはデータ、コードは emit() だけ

ハーネスの追加、差異は原則としてデータ（manifest の宣言）で表現し、コードを書けるのは任意の emit() 1 箇所に限る。この契約により、新ハーネスの追加は「harness/ に 1 ディレクトリ + manifest 1 枚」で済み、共有コードの編集はゼロになる。

5 ハーネスの宣言差分は次の 4 点に集約される。Claude Code が基準形になる。他ハーネスは rules の意味、skills の置き場、フック登録の形式がそれぞれ違うので、その流儀を manifest と adapter で吸収する。

ハーネスharnessDirrulesRenameskills の生成emit()
claude.claudeなしrunner-gen が .claude/skills/ へなし
codex.codexaidlc-rules（.codex/rules は Starlark 権限用のため）emit() が .agents/skills/ へ（runner-gen はスキップ）あり（hooks.json・AGENTS.md も生成）
kiro / kiro-ide.kirosteeringrunner-genなし（IDE は .kiro.hook ファイルを同梱）
opencode.aidlcなしrunner-genあり（.opencode/ ネイティブシェルを生成）
参照: harness/claude/manifest.ts harness/codex/manifest.ts docs/harness-engineering/09-porting-to-a-new-harness.md

モデル tier の投影　判断の重さを 1 語で宣言する

各エージェントの frontmatter は model 名ではなく tier:（judgment / balanced / templated）を書く。「この仕事にどれだけ判断力が要るか」だけを core が宣言し、パック時に各ハーネスの model / effort キーへ投影される。ランタイムのモデル切り替え機構は存在しない。

tier対象エージェントClaude Code への投影意味
judgment9（architect / developer / product ほか）model: inherit（セッションのモデルと effort を継承）判断業務は決して下げない
balanced2（レビュアー 2 体）model: sonnet中型モデルで敵対的レビュー
templated3（delivery / operations / pipeline-deploy）model: sonnet + effort: medium唯一の意図的ダウングレード（定型出力）

コスト上限は AIDLC_TIER_CAP 環境変数、または memory の tier_cap: キー（org → team → project の後勝ち）で一括して下方修正できる。tier は下がる方向にしか動かない。

参照: core/tools/aidlc-tiers.ts:101-125（TIER_PROJECTIONS） scripts/package.ts（projectTierFrontmatter）

プレーンアーキテクチャ　compile 境界で結ばれた 3 面

ランタイムは制御、データ、管理の 3 プレーンに分かれる。ネットワーク機器の分離を借りた設計である。3 面を結ぶのが compile 境界で、ワークフロー開始時に一度だけコンパイルする。実行中は解決済みビューを読むだけで、再コンパイルは次のワークフロー開始時に行う。ルールやセンサーの適用対象を実行中に動的解決しないので、経路が安定する。つまり実行中に挙動が変わらない。

プレーン中身コンパイル成果物
制御（control）ステージ定義・ルール・センサー（「何が走るべきか」のスキーマ）stage-graph.json（各ステージに rules_in_context / sensors_applicable を解決済みで添付。ワークフローの間は安定）
データ（data）ステージ実行・Bolt・エージェント起動（実際の実行）runtime-graph.json（record dir ごと。遷移イベントのたびに再構築される実行の読み取りモデル）
管理（management)/aidlc --doctor・監査クエリ・CLAUDE.mdなし（読み取りと診断のみ）
参照: docs/reference/02-plane-architecture.md core/tools/aidlc-graph.ts（compile の実装）
補足 stage-graph.json と scope-grid.json は core/ には存在しない。32 のステージ .md と 9 のスコープ .md が正で、コンパイル済み JSON は dist/ の各ハーネス配下にのみ置かれ、CI の aidlc-graph compile --check がドリフトを検知する。

インストール　dist をコピーするだけ

インストーラは存在しない。対象ハーネスの dist をプロジェクトへコピーすれば完了する。Claude Code なら cp -r dist/claude/.claude/ your-project/.claude/ と dist/claude/aidlc/ の 2 つで済む。実行時の前提は bun 1 つである。置かれるものはどのハーネスでも 3 点である。エンジン一式の <harnessDir>/、onboarding 文書（CLAUDE.md / AGENTS.md）、即動作するワークスペース雛形 aidlc/ にあたる。雛形には active-space=default と編集可能な memory/ が入る。

参照: README.md（ハーネス別 Quick Start） scripts/onboarding.ts（onboarding 文書の描画器）

非 Claude ハーネスでのフック接続は実行モデルで扱う。adapter がネイティブイベントを Claude 形式に正規化し、バイト同一の core hooks に流す仕組みである。
