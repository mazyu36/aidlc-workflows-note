AIDLC-WORKFLOWS / CONCEPTS

概念 — AI-DLC という方法論

AI-DLC（AI-Driven Development Life Cycle）は、AI 支援開発を承認ゲート付きの 5 フェーズ・32 ステージへ構造化する AWS 発の方法論。このリポジトリはその公式マルチハーネス実装で、方法論が「何を」、各ハーネス配布が「どう」を担う。このページは方法論側の概念モデルを、v2 の実装語彙（space / intent / scope / unit / bolt）とともに整理する。

なぜ構造化するか — アドホック AI コーディングの 3 つの破綻

README は問題を 3 点に絞って宣言する: プロンプト間で文脈がドリフトする、意思決定の理由が記録されない、モデルが頼んでいないことを静かに実行する。AI-DLC の答えは、各ステージに明確な責任者（lead agent）を置き、すべての決定を承認ゲートに通し、ユーザーの修正を永続ルールとして記録して同じ失敗を繰り返させないこと。同一エンジンが使い捨ての PoC も規制産業のエンタープライズ案件も駆動する — 変わるのは実行するステージ数と深度だけ。

出典: README.md docs/guide/00-introduction.md

方法論そのものは 7 つの原則に圧縮されている。全エージェントが毎ステージ読み込む共有ナレッジの冒頭に置かれ、実装のあらゆる設計判断（ゲート、スコープ、標準化された完了メッセージ、矛盾検出）がこの 7 行に遡る。なお、これは方法論仕様の 9 原則（Specification PDF 由来の設計思想）とは別物で、こちらは実行時に守る運用原則にあたる。

パスの注意 原則 3 の aidlc-docs/ は v1 由来の旧表記。v2 の実行時パスは aidlc/spaces/<space>/intents/<YYMMDD>-<label>/（record dir）で、詳細は実行の仕組みで扱う。

ライフサイクル — 5 フェーズ・32 ステージ

ライフサイクルは INITIALIZATION（3）→ IDEATION（7）→ INCEPTION（8）→ CONSTRUCTION（7）→ OPERATION（7）の 32 ステージ。フェーズは順に進み、境界のうち 3 箇所（Ideation→Inception、Inception→Construction、Construction→Operation）にトレーサビリティを検査する検証ゲートが入る。終端の 4.7 を承認するとワークフローが完了するか、1.1 へ戻る反復ループに入る。

フェーズステージ目的出口
INITIALIZATION（0.x）3ブートストラップ — record dir 作成、greenfield/brownfield 判定、状態ファイル生成自動遷移（承認ゲートなし）
IDEATION（1.x）7構想の妥当性検証 — 意図・市場・実現性・スコープ・チーム承認済み initiative brief
INCEPTION（2.x）8要求の精緻化 — 要件・ストーリー・設計・Unit 分解・デリバリー計画実行計画（bolt-plan.md）
CONSTRUCTION（3.x）7構築 — 機能設計・NFR・インフラ・コード・テスト・CI動作しテスト済みのコード
OPERATION（4.x）7デプロイと運用 — パイプライン・環境・可観測性・インシデント・改善監視付きの本番システム

実行トポロジーは 28 ステージが inline（conductor がエージェント人格を纏って対話の中で実行）、4 ステージだけが分散実行になる: 2.2 practices-discovery と 3.5 code-generation は subagent、2.1 reverse-engineering は 2 リンクの pipeline、2.4 user-stories は mob（リードが草稿を書き、互いに盲目な協力者が並列に contribution を書き、リードが統合）。

参照: core/aidlc-common/stages/（32 ステージの正） docs/guide/04-phases-and-stages.md stage-graph.json（コンパイル済みグラフ）

Bolt と walking skeleton — Construction の実行単位

Construction は「Bolt ごと」に走る。Bolt は 1 つの Unit（または依存で結ばれた小さな Unit 群）に対する 3.1–3.5 の 1 パスで、最初の Bolt はアーキテクチャを end-to-end で証明する最小スライス = walking skeleton としてゲート付き・対話的に実行される。skeleton 承認直後に ladder prompt が 1 回だけ発火し、「以降を自律実行するか、Bolt ごとにゲートするか」の選択が状態に記録され、残り全 Bolt を統べる。この形に至った経緯がガイドに明記されている。

自律モードでも止まる箇所が 1 つだけある。Bolt のコード生成が失敗したとき、ワークフローは autonomy 設定にかかわらず必ず停止し、Retry / Skip / Abort を提示する（halt-and-ask）。失敗した worktree は保全され、判断は常に人間に返る。

参照: core/aidlc-common/protocols/stage-protocol.md（halt-and-ask 規定）

概念モデル（用語）

v2 の語彙は「どこで作業するか」（workspace / space / intent）、「何を実行するか」（stage / scope / depth / unit / bolt）、「誰が動かすか」（engine / conductor / agent）、「何が品質を守るか」（gate / sensor / rule / audit / learnings)の 4 群に分かれる。

用語定義出典

Spaceチーム単位の世界 aidlc/spaces/<space>/。memory / knowledge / intents を持つ。既定は defaultglossary
Intent1 件の作業。intents.json のレコード（uuid / slug / scope / status）+ 専用 record dirguide/03
Stage32 ある実行単位。lead agent・入出力契約・ステージプロトコルを持つglossary
Scope9 つの実行構成。どのステージを EXECUTE/SKIP にするかの行列。自動判定もあるguide/05
DepthMinimal / Standard / Comprehensive。各ステージが生む詳細度。スコープとは直交guide/05
Unit2.7 units-generation で分解される、独立実装可能なソリューション断片glossary
BoltUnit（群）に対する 3.1–3.5 の 1 パス。初回 = walking skeletonglossary

スコープと深度 — 同じエンジン、違う量

スコープは 32 ステージの EXECUTE/SKIP 行列。bugfix は 7 ステージ（初期化 3 + reverse-engineering / requirements-analysis / code-generation / build-and-test）まで削り、enterprise は 32 全部を Comprehensive 深度で回す。深度は「どのステージを実行するか」ではなく「各ステージがどれだけ詳細に作るか」を変える独立の軸で、テスト戦略（テストをいくつ書くか）も 3 段階の独立軸として持つ。

スコープEXECUTE / 32既定深度想定用途
enterprise32Comprehensive規制・大規模。全ステージ + 全部の重み
feature32Standard既定スコープ。全ステージを標準の重みで
workshop25Standard（テストのみ Minimal）ファシリテーター主導の演習。Ideation 7 つを全部スキップ
mvp22Standard市場調査・チーム編成・Operation 全 7 つをスキップ
infra13Standardインフラ専業。ストーリー・モックアップ系を持たない
security-patch10MinimalNFR 要件 + デプロイ 2 ステージを含む最短修正
poc / refactor8Minimal検証・整理の最小構成（refactor は + functional-design）
bugfix7Minimal最小。意図確認すらスキップし再現から入る

スコープはコマンドで明示指定するほか、自由文の意図からキーワードで自動判定できる。さらに /aidlc compose は composer エージェントが実装エントロピーを 5 成分でスコアし、既成の 9 択に頼らない最小構成の EXECUTE/SKIP 行列をその場で組む。

参照: core/scopes/（9 スコープの正） scope-grid.json（コンパイル済み行列） docs/guide/05-scopes-and-depth.md

対話モードと承認ゲート

ステージ中の入力方法は 3 モードあり、どれを選んでも同じ questions ファイルに収斂するため途中で切り替えても進捗を失わない: Guide Me（構造化質問に 1 問ずつ答える）、Edit File（空欄付きの質問ファイルを直接編集）、Chat（自由対話から決定事項を抽出して書き戻す）。

承認ゲートは Initialization を除く全ステージの末尾に立つ。選択肢は Approve / Request Changes の 2 択で、「次のステージ」の表示名はエンジンが計算するため常に正しい。承認には実際の人間のターン（HUMAN_TURN 監査イベント）が必要で、autopilot のモデルが承認を偽造することはできない。reject が 3 回続くと Accept as-is（現版をアーカイブして先へ進む）の第 3 選択肢が現れ、Ideation / Inception のゲートに限り、スコープでスキップされたステージをその場で追加する選択肢が出ることもある。

参照: docs/guide/07-interaction-modes.md

ゲートの強制力はプロトコル文書とフックの両方で担保される。仕組みの詳細は実行の仕組み、レビュアー・センサー・学習ループとの重なりはエージェントと品質を参照。
