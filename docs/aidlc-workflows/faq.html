AIDLC-WORKFLOWS / FAQ

FAQ　coding agent 経験者の想定問答

coding agent を日常的に使う開発者に AI-DLC Workflows v2 を紹介したとき、実際に出る順で質問と答えを並べた。答えの根拠はすべて基点コミットの公式 docs にあり、各回答末尾のリンクから日本語版で確認できる。詳細な図解は解説各ページ（仕様、モデル、構成、実行、検証）が受け持つ。

位置づけ

AI-DLC Workflows とは何か

AWS が定義する AI 主導開発の方法論 AI-DLC の公式実装で、awslabs の OSS である。開発ライフサイクルを 5 フェーズ（initialization、ideation、inception、construction、operation）、32 ステージに構造化し、承認ゲート付きで coding agent に実行させる。単一の core/ から Claude Code、Kiro CLI、Kiro IDE、Codex CLI、opencode の 5 配布物を生成する。

参照: core/ harness/ dist/

CLAUDE.md とスキルを整備すれば同じことができるのでは

プロンプト資産は助言であり、agent が従うかは確率的である。AI-DLC は工程管理を TypeScript のコードに移した。次にどの stage を実行するか、承認されたか、何が起きたと記録するかを LLM は 1 つも決めず、決定論の engine が型付き directive で指示する。公式 docs の原則は「TypeScript が決定論的な記帳を所有し、LLM が判断を所有する」で、並列マージの保留のような不変条件は散文ではなくツーリングで強制される。

出典: reference/03 Orchestrator・reference/12 State Machine

Kiro の spec-driven development と何が違うのか

Kiro の spec は 1 機能の要件、設計、タスクを Markdown 化する仕組みで、対象は実装前の合意形成にある。AI-DLC は要求から運用までのライフサイクル全体を対象に、14 の役割別エージェント、工程間の受け渡し、承認ゲート、チーム知識の蓄積までを規定する。Kiro CLI / IDE は AI-DLC を実行するハーネスの 1 つ、という関係になる。

出典: guide/04 Phases and Stages

Claude Code 専用か

5 ハーネス対応で、移植ではなく生成である。決定論的な core/ が 1 つあり、scripts/package.ts が各配布物を生成する。エンジン、状態機械、audit、グラフ、swarm レフェリー、learnings ゲートは全配布物でバイト同一で、docs は「異なるのはシェルだけ」と述べる。dist/ を手で編集すると CI のドリフトガードが落ちる。

参照: scripts/package.ts

出典: guide/harnesses・解説: リポジトリ構成

v1 と v2 は何が違うのか

5 フェーズの方法論は v1 から変わっていない。v2 が作り直したのはワークフロー層で、機械が検査できる範囲を広げて人間の介入を削ることと、細粒度で組み替え可能な部品化が再設計の動機である。リポジトリも別物で、main ブランチは v1 系のツリーを保持する。資料は v2 ブランチ / v2.x タグを見ること。

出典: 解説: 方法論仕様

AWS 専用か

方法論と実装は汎用で、AWS アカウントは必須ではない。AWS 固有の知識は aws-platform や pipeline-deploy という担当エージェントに局所化されている。モデルアクセスに Amazon Bedrock を使う手順は任意の選択肢として用意されている。

出典: guide/01 Getting Started

仕組みの核

三区画モデルとは何か

stage（工程）を「AI に実行させられて、結果を機械で検証できる」形で書くための宣言テンプレートである。どんな工程も 3 つの欄で書く。第 1 欄 What は入力と出力。第 2 欄 How Do We Know It's Right は出力が正しいと判定する条件で、AI が書き換えられないプログラム検査の形で書く。第 3 欄 What Did We Learn は実行から得た学びの記録先で、学習ループの入力になる。

第 2 欄があると、AI は生成 → 機械検査 → 不合格なら修正のループを人間なしで回せる。合格したら進んでよく、規定回数失敗したら人間へエスカレーションする。実例を挙げると Reverse Engineering stage は、What = コードベースを受け取り 9 個の分析文書を出す、検証 = 9 個すべての存在をツールが確認してから承認ゲートを開く、である。仕様全体の主張は「機械検査できる事後条件を増やした分だけ、人間の承認を外せる」であり、ゲート削減の根拠はこの欄の充実度になる。

出典: 解説: 方法論仕様・reference/15 Stage Definition

どこが決定論で、どこが確率的か

仕事量の大半（要件を書く、設計する、コードを書く）は LLM が担う。一方でワークフローの進行に関する判断は 1 つ残らず TypeScript コードが担う。scope 判定、stage ルーティング、ジャンプ検証、ゲート状態、完了判定は engine が、状態遷移と audit 記録は専用ツールが、並列の審判とループ強制は hook が行う。LLM は作業を終えるたびに engine へ report し、返ってくる directive に従う。「終わった」という LLM の自己申告ではなく、ツールが書いた状態ファイルと audit だけが正である。

出典: reference/03 Orchestrator・解説: 実行モデル

技術要素はそれぞれ何を担っているのか

役割は 4 層に整理できる。ステアリング層の文書がすべて「お願い」に留まるわけではない点が要で、工程の骨格はコンパイルされて決定論層に昇格し、engine は Markdown ではなくコンパイル済み JSON だけを読む。

層構成要素役割従わせる力
人間の判断承認ゲート（AskUserQuestion）・ladder prompt・halt-and-ask進行可否の最終判断。機械検査できない部分の引き受け先人間
決定論engine（aidlc-orchestrate.ts、サブコマンドは next / report / park）・hook 14 本・ツール 32 本・コンパイル済み表（stage-graph.json / scope-grid.json）・実行系 bunルーティング・状態遷移・audit・並列の審判・ループ強制。判断は型付き directive として発行絶対（コード実行）
ステアリングSKILL.md（conductor）・stage-protocol.md + stage 定義 32・agent 定義 14・knowledge 59・scope 宣言 9・rules / practicesLLM への手順・ペルソナ・知識・規範の供給確率的。結果はゲートと事後条件で検査
記録aidlc-state.md・audit シャード・record dir の成果物・codekb・runtime-graph.jsonワークフローの正。再開・復旧・実績グラフの源書き込み経路をツールに限定

層をつなぐ橋は 2 つある。第 1 が compile である。stage 定義の YAML と scope 宣言は aidlc-graph.ts compile が stage-graph.json / scope-grid.json へ変換し、手編集は CI の compile --check が検出する。第 2 が学習ループである。実行シグナルを sensor（blocking / advisory の 2 段階）が検知し、learnings ゲートを通過したものだけが rules へ還流する。

参照: core/hooks/ core/tools/ core/knowledge/

出典: reference/15 Stage Definition・reference/17 Engine and Skill System

動作の流れ　1 つの stage はどう進むのか

conductor（LLM）と engine（決定論）の往復が骨格で、hook がその外側で自動発火する。engine の next が「次に実行する stage」を directive で指名し、conductor が実行し、人間のゲートを経て report で返すと、engine が audit を書いてから状態を進めて次の directive を返す。このループが workflow 完了まで続く。

stage の実行形態は stage 定義が宣言し、inline、subagent の hub-and-spoke、mob、pipeline の 4 形がある。どの形で走るかも conductor の裁量ではなく定義データ側にある。

出典: reference/03 Orchestrator・reference/04 Stage Protocol

bun は何を実行していて、誰がいつ呼ぶのか

bun は 14 本の hook と 32 本のツール（すべて TypeScript）の実行系である。職務は状態管理、audit 記録、sensor ディスパッチ、runtime-graph のコンパイル、ループ強制、状態遷移と reviewer スコープの強制、statusline、human-turn の記録で、起動約 20ms、追加依存なし、macOS / Linux / Windows で同一に動く。

呼び出し経路は 2 つある。経路 A はハーネスが呼ぶ。Claude Code のライフサイクルイベント（SessionStart、SessionEnd、コンパクション直前ほか）が settings.json にプロジェクト全体で登録された hook を必ず実行し、LLM は介在できない。各 hook は self-gate していて、アクティブなワークフローが無ければ即終了するため、AI-DLC の外の通常利用では no-op になる。

経路 B は LLM が CLI として呼ぶ。conductor が bun で engine（aidlc-orchestrate.ts）の next を実行して directive を受け取り、stage 実行後に report で結果を返す。状態と audit の書き込みも専用ツール経由に限られる。経路 B の呼び忘れや逸脱は経路 A の hook（状態遷移とループの強制）が検査するので、LLM のサボりで工程管理は破綻しない。

出典: reference/06 Hooks and Tools・guide/01 Getting Started

素の Claude Code の設定機構とはどう対応するのか

Claude Code ユーザーが普段使う機構が、そのまま AI-DLC の部品として使われている。対応は次のとおりで、他ハーネスでは hook の配線先だけが差し替わり（Kiro CLI = agents/aidlc.json、Kiro IDE = .kiro/hooks/、Codex = .codex/hooks.json、opencode = plugin）、決定論層のコードはバイト同一のまま動く。

Claude Code の機構AI-DLC v2 での使い道
hooks（settings.json 登録）強制の土台。14 本すべてをプロジェクト全体に登録し、self-gate で AI-DLC 外では no-op
skillsconductor（SKILL.md、/aidlc で起動）と stage-protocol・32 stage ファイル。エントリポイント兼実行手順
subagents14 の役割 agent。tier 宣言をハーネスごとに model + effort へ射影
permissions組み込みツールの事前承認。ワークフロー中の許可プロンプトを消す
CLAUDE.md に相当する常設規範rules / practices が担当。5 レイヤー継承・strict-additive で、上書きは audit に記録
MCP任意の外部統合。.mcp.json で宣言し Claude Code の MCP レイヤーが管轄

出典: reference/14 Claude Features（コンセプトからプリミティブへのマッピング表がある）

実行モデル

人間の承認ゲートはどこに入り、外せるのか

既定は全部ゲートである。Initialization の 3 stage を除く全 stage が構造化 UI（AskUserQuestion）による明示承認を要し、標準は Approve / Request Changes の 2 択、修正 3 回で発動するエスケープハッチを持つ。ゲートは状態機械の AwaitingApproval に対応し、拒否は Revising に遷移する。

自律を選べるのは Construction だけである。最初の Bolt（walking skeleton）は必ずゲート付きで、出荷直後に ladder prompt が 1 回だけ「以後は自律か、Bolt ごとにゲートか」を聞き、選択は aidlc-state.md に永続して再開後も有効になる。チームの常設方針は practices に書け、個別ワークフローの計画と衝突したら practices が勝つ（上書きは audit に PRACTICES_OVERRIDE として記録）。ゲートを外してよい範囲は、機械検査できる事後条件をどれだけ書けたかで決まるというのが仕様の答えである。

出典: guide/07 Interaction Modes・reference/04 Stage Protocol

並列実行はどう分離され、失敗はどう扱われるのか

並列の単位は Bolt（1 つの Unit に対する stage 3.1–3.5 の 1 パス）で、並列にできる形は units-generation stage が作る依存 DAG がデータとして決める。conductor は 1 メッセージで Unit ごとに並列の subagent を発行し、作業分離は git worktree ツールが担う。同一バッチで複数 Bolt が失敗すると、成功分はマージ保留（HOLD-MERGE 不変条件）になり、失敗は 1 件ずつ halt-and-ask で人間に順番に上がる。ファシリテーター 1 人と参加者 N 人が別々の Bolt を進める workshop scope もある。

出典: harness-engineering/08 Construction and Swarm・guide Workshop モード

状態と監査はどう壊れないようにしているのか

workflow、phase、stage の 3 つの入れ子状態機械と、ハーネスのセッションイベントの計 4 ストリームが intent ごとの audit trail を共有する。不変条件は「すべての状態遷移はツールが所有する emitter をちょうど 1 つ持つ」で、LLM の散文から audit を書くことは禁止されている。さらに audit-first atomicity（ツールは状態を変更する前に audit を書き、audit が失敗したら状態に触れる前に throw する）により、audit と状態ファイルは食い違わない。承認ゲートのたびに audit から runtime-graph.json（実績のグラフ）が実体化され、計画側の stage-graph.json と突き合わせられる。

出典: reference/12 State Machine・reference/13 Runtime Graph

コンテキストのリセットは誰がいつやるのか

リセット操作（/clear や新セッション開始）は人間の操作で、フレームワークが会話を自動リセットすることはない。フレームワークが肩代わりするのは 3 つある。第 1 に、いつ切られても復旧できる設計である。成果物、状態、audit はディスクにあり、次の /aidlc で SessionStart hook が再開コンテキストを注入し、再開オプションは 4 つある。第 2 に、リセットし忘れて自動コンパクションが起きた場合の防御である。直前に hook が復旧ファイル .aidlc-recovery.md を書き、次回起動時に状態と突き合わせて食い違いを警告する。第 3 に、肥大しにくい構造である。stage の実作業は役割エージェントの subagent に分かれ、各 subagent は新しいコンテキストで走る。

切るタイミングの規定は docs に無い。状態がディスク上で確定する承認ゲートの直後が安全な切れ目になる、というのは状態機械の性質から導ける運用指針である。

出典: guide/11 Session Management

Reverse Engineering は何をしているのか

brownfield プロジェクト限定の Stage 2.1 で、initialization の決定論スキャナ（ルールベース。プロジェクト直下と既知のソースディレクトリを走査）が brownfield と判定した場合だけ走る。実行は 2 リンクの pipeline で、developer エージェントがコードベース全体をスキャンし、architect エージェントが結果を 9 個の成果物へ統合する。内訳は business-overview、architecture（相互作用図つき）、code-structure、api-documentation、component-inventory、technology-stack、dependencies、code-quality-assessment、reverse-engineering-timestamp である。

出力先は intent の外の永続ストア aidlc/spaces/<space>/codekb/<repo>/ で、以後の Inception、Construction 全 stage の土台になる。成果物が既にあっても毎回再実行する always-rerun ポリシーを持ち、古いスナップショットに基づく設計を防ぐ。

出典: reference/04-stages Inception・guide/02 Your First Workflow

導入と運用

32 ステージは小さなタスクには重すぎないか

scope が実行する stage を選ぶ。9 種（poc、mvp、feature、bugfix、refactor、security-patch、infra、enterprise、workshop）があり、bugfix は最小、enterprise はフル構成である。さらに depth（3 段階）が各 stage の成果物の詳細度を、テスト戦略がテスト生成量を制御する。この 3 つで、包括的なエンタープライズ機能から素早い bugfix までをタスクに合わせる。

参照: core/scopes/

出典: guide/05 Scopes and Depth

既存コードベースに途中から導入できるか

できる。initialization のスキャナが greenfield / brownfield を自動判別し、brownfield では Reverse Engineering が走って既存コードの分析文書を作り、以後の設計の土台にする（前節参照）。Practices Discovery stage は既存チームの開発規約を発見して space の memory 層へ昇格させる。

出典: guide/02 Your First Workflow

成果物はどこに残るのか

すべてリポジトリ内のファイルである。aidlc/spaces/<space>/ 配下に intents（ワークフロー単位の成果物と audit）、knowledge、codekb、memory/team.md が置かれ、状態は aidlc-state.md に入る。全部 git 管理なので、レビューも履歴追跡も普段の PR フローに乗る。

出典: guide/14 Artifacts Reference

チームの規約と学びはどう蓄積されるのか

2 系統ある。チームの常設ルールは practices として書き、rule システム（5 レイヤー継承、ファイル名由来の scope、strict-additive なランタイムモデル、rule-drift 検出）が管理する。実行中の学びは sensor が検知し、learnings ゲートを通過したものだけが rules へ還流するので、無条件に増殖しない。エージェントの役割知識は 59 ファイルの knowledge として同梱される。

出典: guide/09 Rules and the Learning Loop・reference/08 Rule System

自社の開発プロセスに合わせて拡張できるか

Harness Engineering ガイドに公式手順がある。stage 追加、エージェント追加、scope、sensor の追加、新しいハーネスへの移植、プラグイン作成まで章立てされており、core/ を 1 箇所直せば 5 配布物すべてに反映される。

出典: harness-engineering/00 Overview

ハーネスごとの制約差はないのか

コアはバイト同一だが、シェル側の制約は実在し、docs が実測ベースで明記している。Codex CLI は 0.145.0 以上をピンし、/aidlc --doctor が強制する。opencode は *.ts の自動インポートがエンジンスクリプトでクラッシュするため、エンジンツリーを .aidlc/ に隔離する 2 ディレクトリ構成をとる（1.17.18 でライブ再現の上での設計）。Kiro IDE は世代で hook のペイロードチャネルが違い、probe による実証リファレンスが同梱されている。制約を隠さず版数と再現条件つきで書いてあるのがこのリポジトリの流儀である。

出典: guide/harnesses Codex CLI・guide/harnesses opencode・reference Kiro IDE hook payload

モデルは何を使うのか

ハーネスの設定に従う。エージェント定義は tier を宣言し、ハーネスごとに model + effort へ射影される。Codex 配布物の同梱 config.toml は既定が Amazon Bedrock で、OpenAI 認証への切り替えもできる。

出典: reference/14 Claude Features・guide/harnesses Codex CLI

トークン消費はどれくらい増えるのか

公式の実測値は示されておらず、定量では答えられない。多段の成果物生成と役割別エージェントのぶん、素の 1 セッションより確実に増える。制御レバーは scope、depth、テスト戦略で、小タスクに enterprise scope を使わないことが実務上の答えになる。

ライセンスと本番利用の位置づけは

awslabs の OSS で、ライセンスは MIT-0（MIT No Attribution）である。AWS のサービスではないので SLA やサポートは無い。v2 は v2.x タグのリリースラインだが開発が活発で、docs はほぼ毎日動く。導入するならタグかコミットで固定し、追随を計画的に行うのが現実的である。

まず何をすれば試せるのか

前提ツールは対応ハーネスのどれか 1 つと bun である。bun は 14 本の hook と 32 本のツール（すべて TypeScript）の実行系で、起動約 20ms、追加依存なし、macOS / Linux / Windows で同一に動く。配布物をプロジェクトにコピーすれば始められ、MCP サーバーや Bedrock 連携は任意になる。最初は poc か feature scope で小さく 1 周回すことを勧める。

出典: guide/01 Getting Started
