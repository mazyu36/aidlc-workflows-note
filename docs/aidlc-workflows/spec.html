AIDLC-WORKFLOWS / SPEC

方法論仕様　AI-DLC Workflows 2.0 Specification を図で読む

機械が検査できる事後条件を増やした分だけ、人間の承認を外せる。これが v2 の設計判断すべてを貫く 1 本の主張である。同梱の仕様書（PDF・6 ページ）はこの主張を 9 原則へ展開し、三区画モデルという器と自己修正ループで運用可能にする。このページは 9 原則を原典の論拠まで開き、器とループを図解し、v2 実装との対応表で締める。

原典: assets/AI-DLC-Workflows-2.0-Specification.pdf

仕様の位置づけ　方法論は据え置き、ワークフロー層だけ作り直す

v2 が書き換えたのはワークフロー層だけである。5 フェーズの方法論は v1 から変えていない。v1 が実証したのは「人間を輪に入れた stage 列で SDLC を回す」価値である。v2 はその上で、機械が検査できる範囲を広げて人間の介入を削る。

再設計を駆動した力は 2 つ。第一に、顧客が細粒度で組み替え可能な部品を求めた。自分たちのデリバリーフローに合わせるためである。第二に、エージェント基盤が成熟した。Skills、マルチエージェントランタイム、決定論的ライフサイクルフック、MCP が揃い、粒度と検証をネイティブに表現できるようになった。

9 つの原則　自律は「判断の蒸留」の漸進で達成する

9 原則は 1 本の論理でつながる。人間の判断は機械実行可能な形へ蒸留できる（P1）。ただし intent は曖昧に始まるので、仮定せず明確化してから解く（P2）。事後条件があれば AI は停止条件つきで自己修正できる（P3）。その事後条件を収める器が三区画モデルだ（P4）。器はあらゆる SDLC ステージに適用できる（P5）。一撃圧縮は爆発するので段階分解する（P6）。蒸留は一晩で終わらないから安全な増分で進める（P7）。拡張可能性は最初から設計する（P8）。実践の学びで検証ルールを育てる（P9）。

2 つの「原則」を混同しない ここで扱う 9 原則は Specification PDF が定める v2 の設計思想である。方法論モデルページに出てくる 7 Core Principles は、全エージェントが毎ステージ読む共有ナレッジ（ai-dlc-principles.md）の運用原則で、これとは別物。9 は「なぜこの設計にするか」、7 は「実行時に何を守るか」を述べる。
#原則主張の要点
1人間の判断は機械へ蒸留できる判断・検証・操舵に費やす人間の労力は、判断パターンの体系的な蒸留で削減できる。自律への前提条件
2すべての intent は曖昧に始まる（それで良い）AI は仮定せず明確化質問で曖昧性を解消してから解く。欠陥ではなく自然な初期条件として受け入れる
3Safety Net 付きの自己修正ソルバーAI が改変できないプログラムで検査可能な事後条件 + 扱いやすい成功基準 + 安価な反復、の 3 条件で収束する。停止条件（反復上限 / トークン予算）に達したら人間へエスカレーション
4三区画モデルstage を What（入出力）/ How Do We Know It's Right（事後条件）/ What Did We Learn（実行時の学び）の 3 区画で宣言する
5あらゆる SDLC ステージが同じ器に収まる実装系だけでなく、要件・設計・デプロイ・監視も「入力 → 出力の変換 + 明示的な事後条件」で記述できる
6一撃圧縮ではなく段階分解「このアプリを作って」1 発は事後条件の爆発と組合せ探索の爆発で破綻する。細粒度の部品 = Skills を合成単位に、stage / phase は柔らかい編成概念にする
7ビッグバンではなく安全な増分での自律化手持ちの規約から始め、guardrail を漸進的に事後条件へ蒸留（hydration）し、安全な増分の幅を広げる
8拡張可能性は基礎制約追加（additive）・置換（replacement）・合成（composability）の 3 形態を、ベンダー基準と同じ構文・同じ保証で顧客に開く
9実践からの学習（Compound Engineering）人間の修正・やり直し・escape-hatch 受諾を候補ルール化し、人間の承認を経て有効ルールへ昇格する。手作業の執筆だけに頼らない hydration 経路

各原則の論拠と具体例を以下に開く。表は要点の索引、ここは原典の散文にあたる。

原則 1　人間の判断は機械へ蒸留できる

判断パターンを機械実行可能な形へ蒸留すれば、人間の労力は削れる。判断・検証・操舵に費やす分の相当部分が対象になる。これが自律へ近づく前提条件になる。原典は限界も明言する。human-in-the-loop を完全に除去できるかは、まだ合意に至っていない。ただし「すべての stage で人間の労力を下げ続ける」ことは必須として一致する。現状の AI-DLC は全 stage で人間に依存するが、それを恒久の前提ではなく最適化対象の初期条件として扱う。

原則 2　すべての intent は曖昧に始まる（それで良い）

曖昧さは欠陥ではなく初期条件である。だから AI は仮定を置かず、明確化質問で intent を絞ってから解き始める。曖昧さの源は 3 つある。人間の仕様記述能力の限界、本人も気づかない unknown-unknowns、自然言語そのものの多義性が挙がる。「売上ダッシュボードを作って」には、どの指標を・どの期間で・誰に向けて・何のために、という前提が言われないまま潜む。intent statement を事前に整えるほど、この stage は速くなる。

原則 3　Safety Net 付きの自己修正ソルバー

事後条件を渡せば、AI は検証と修正を反復して解へ収束する。入力と期待される出力、そして健全で完全な事後条件が揃った場合に限る。収束は 3 つの構造的性質に依存する。事後条件が AI に改変できないプログラムで検査できること、成功基準が扱いやすいこと、反復が安価で多数の候補を試せることである。Build & Test やインフラのプロビジョニングはこれを満たすので、収束まで自己修正できる。要件分析・設計批評・UI モックアップは満たさないので、事後条件が育つまで人間の検証を残す。

ただし妥当な時間とトークン予算で解けない問題もある。だから自己修正ループには停止条件を必ず置く。反復回数の上限、またはトークン予算を用いる。収束できなければ無限に回さず人間へエスカレーションする（参考: AI Agents as Universal Task Solvers、Karpathy の autoresearch）。

原則 4　三区画モデル

原則 3 を運用可能にする器が三区画モデルである。stage の仕事を 3 区画で表す。区画 1 が生成仕様、区画 2 が自己検証仕様、区画 3 が学習仕様である。

区画 1「What」は入力と出力を宣言する。User Stories を入力に取り Domain Model を出力する、という形をとる。下流の品質が依存する中間成果物も、命令ではなく追加の出力として名指す。Bounded Contexts Design なら、途中の event・aggregate・bounded context 境界の識別がそれにあたる。こうすると区画 1 は宣言的なまま、必要な成果物の生成を保証できる。

区画 2「How Do We Know It's Right」は事後条件を定義する。正しい出力が満たすべき規則・制約・品質チェックを指す。区画 3「What Did We Learn」は実行時の学習捕捉を定義する。どの観測が候補ルールや事後条件になり、区画 2 や共有 guardrail ライブラリへどう昇格提案されるかを書く。

2 区画のどちらが欠けても AI は動けない。事後条件がなければ自己修正できず、入出力がなければ何を解いているか分からない。事後条件は最初から健全かつ完全には揃わないので、初期は人間の検証へ頻繁にエスカレーションする。ダッシュボード生成なら当初は配色を人間に確認する。組織の UI 標準とその逸脱を検査する事後条件を与えれば、その確認は消える。

原則 5　あらゆる SDLC ステージが同じ構成に収まる

この器は実装系の stage 専用ではない。要件明確化・アーキテクチャ設計・デプロイ・監視も同じ形で書ける。stage が創造的でも分析的でも機械的でも、「定義された入力から期待される出力への変換を、明示的な事後条件で統制する」形に落ちる。（原典の見出しは "Two-Compartment Construct" だが、本文は three-compartment を指す。ここでは三区画で統一した。）

原則 6　一撃圧縮ではなく段階分解

「このアプリを作って」の 1 発でデプロイまで到達する道は選ばない。実際的でないためである。理由は 2 つある。

  1. 事後条件の爆発。機能正しさ・コード品質・セキュリティ・コンプライアンス・性能・アクセシビリティを一度に検証すると、基準が相互依存して絡む。単一 stage での定義と管理は破綻する。
  2. 組合せ探索の爆発。制約を同時に課すと解空間が巨大化し、長時間または非停止のループになる。原則 3 の停止条件が防ごうとする暴走を、構造の側から招くことになる。

この 1 年の顧客からの学びも同じ方向を指す。規範的すぎる stage 定義が導入摩擦を生んだ。AI-DLC 1.0 は Build & Test を 1 stage とするが、実際にはレビュー・ビルド・機能テスト・セキュリティテストの複数活動にまたがる。UI モックアップを User Stories と並行して作る顧客もいれば、Design stage へ遅らせる顧客もいる。

そこで合成単位を Skills に移す。Skills はデータベース設計・コードレビュー・セキュリティ分析といった、従来は人間が提供してきた能力の単位を指す。その ai-native 表現（agentskills.io の仕様）が、指示・ツール・参照を実務者になぞらえてモデル化する。stage と phase は Skills を束ねる柔らかい編成概念に退く。Skills のライブラリ自体も原則 4 の三区画モデルで設計する。

原則 7　ビッグバンでなく安全な増分での自律化

一夜で完全な自律には到達できない。組織は guardrail・no-go-zone 規則・コンプライアンス要件・セキュリティポリシー・ドメイン固有制約を大量に抱えている。AI が自律で動くには、それらを機械実行可能な形へ蒸留する必要がある。蒸留には時間と組織的合意と反復が要るため、本質的に漸進的である。

規制の厳しい大企業を考えれば分かる。社内コード標準・セキュリティレビューゲート・アーキテクチャ統制方針は、文書・暗黙知・レビューチェックリスト・人間の判断に散っている。これを一度に区画 2 へ翻訳しきれる顧客はいない。AI-DLC 2.0 はこれを阻害要因ではなく、想定される導入経路として受け入れる。

  1. 手持ちから始める。すでに符号化できる事後条件を定義する。コード標準・命名規約・基本的なセキュリティ規則がその範囲に入る。境界の内側は AI が自律で動き、外は人間へエスカレーションする。
  2. 漸進的に hydration する。guardrail・コンプライアンス・ドメイン規則を区画 2 へ蒸留していく。追加のたびに AI が自律で検証できる範囲が広がる。
  3. 安全な増分を広げる。ライブラリが成熟すると、一度に安全に実行できる幅が伸びる。各ステップで人間の判断を要した作業が、複数 stage を跨いで自律進行するようになる。

原則 8　拡張可能性

拡張可能性は後付けの便利機能ではなく、基礎の設計制約に置く。すべての顧客の guardrail・コンプライアンス義務・ドメイン固有ワークフロー・組織標準を先回りで予期できないためである。顧客はベンダー提供のベースラインと同じ構文、同じ保証で拡張・改変・合成できる必要がある。支えるシナリオは 3 つある。

  1. 追加的拡張。既存の AWS ベースライン定義の上に、自前の補足規則と事後条件を重ねる。
  2. 置換的拡張。要件がベースラインと乖離する箇所で特定の規則を置換し、以後その stage 定義の所有権を引き取る。
  3. 合成可能性。同じ三区画構成で著述したまったく新しい stage を導入し、AI がそれをワークフローへ賢く縫い込む。

原則 9　実践からの学習（Compound Engineering）

Skills は著述時だけでなく、使われながら改善する。各 Skill は生成仕様・検証仕様と並べて、実行時の相互作用から何を学ぶかを宣言する。学習源は人間の修正・再実行・escape-hatch の受諾である。その観測がどう区画 2 や共有 guardrail ライブラリへの候補になるかも書く。この層がなければ、原則 7 の hydration は手作業の著述だけに依存して遅れる。

今日は、人間が AI の出力を修正しても一度で忘れられる。原則 9 の下では修正が学習候補になる。ユーザーが要件文書の同じ節を毎回書き直すなら、その stage はパターンを捉える事後条件を提案する。特定の設計判断を繰り返し覆すなら guardrail を提案する。提案は有効ルールへ昇格する前に人間の承認を求める。こうして実践が検証ライブラリの hydration 源になる。

三区画モデルと自己修正ループ　仕様の心臓部

実行モデルの核は 1 行に収まる。三区画で宣言された stage を、停止条件つきの自己修正ループで解く。区画 3 が学びを捕らえ、承認を経て区画 2 を太らせる。これを hydration と呼ぶ。ループが回るほど検証が濃くなり、人間の出番が減る。

区画 2 の検証は 2 形態に分かれ、性質がまるで違う。推論的検証は LLM 指示で書き、合否で切れない品質ヒューリスティクスに使う。コードレビュー規範の大半がこれにあたる。ただし生成者と同じモデルが自然言語の検査を判定すると、文言は満たすが意図を外す危険がある。だから LLM 判定の事後条件しか持たない stage は自己停止せず、必ず人間の検証に出す。

計算的検証は実行可能物で書き、曖昧さゼロで強制すべき規則に使う。「本番の CloudFormation スタックを削除するコードパスを許さない」「認証なしの API エンドポイントを公開しない」がその例である。判定は決定論的になる。検証ルールを実行可能物へ蒸留するほど（原則 7）、人間の介入なしに自己停止できる stage が増える。

構造　5 つの構成要素と DRY

構造は 3 つのライブラリと 2 つの機構でできている。ライブラリは Persona-Agents・Stages・Knowledge。機構は、それらを適応的ワークフローへ合成する orchestrator と、ツール別の構成物へ投影する package manager である。設計原則は DRY、関心の分離、そして各ツールのネイティブ機能を最大限使うこと（最小公倍数に落とさない）の 3 つになる。

orchestrator の 5 機能

orchestrator は Skills を合成・順序付け・監視・適応させ、end-to-end の開発フローにまとめる。組み立て方は各 stage が宣言するメタデータで決まる。読むのは 3 つある。区画 1 の入出力（形式と依存の期待を含む）、stage の目的、そして orchestrator ヒント（順序制約・条件つきトリガ・エスカレーション方針）である。

第一がゴールの所有である。end-to-end の目的を握り、宣言された成果に責任を負う。ゴール追跡を個々の stage へ委譲せず、全 stage の集計出力が元の intent を満たすことを保証する。

第二がワークフロー構成で、離散的な stage を適応的ワークフローへ組み上げる。判断材料は 4 つある。intent の性質（greenfield とバグ修正では並びが違う）、利用可能な context（文書が揃っていれば stage を省略できる）、stage の出力と実行時シグナル、そして orchestrator ヒントつきの顧客作成 stage（原則 8）である。固定パイプラインには従わない。順序つきの plan は持つが、実行中も書き換わる。

第三がルーティング・可観測性・制御、つまり運用の制御面にあたる。先行出力や元の intent から正しい入力を引いて stage を起動する。実行状態（走った stage・結果・成果物）を追跡し、原則 3 の停止条件を強制する。収束できない stage は一時停止して人間へ上げ、解決後に再開する。どの stage をなぜどの順で起動したかは、すべて監査証跡に残す。

第四が抽象化境界である。各 stage をブラックボックスとして扱い、内部には干渉しない。完了時に宣言された事後条件の充足だけを検証する。この分離が stage の独立進化を許す。

第五が stage 横断の不変条件の実施にあたる。命名規約・セキュリティポリシー・文書標準はワークフロー全体にまたがる。これらを適切なチェックポイントで評価し、どの stage 単独の責任でもないグローバル制約として強制する。

ここまでは仕様の抽象定義である。v2 での実体（決定論エンジン aidlc-orchestrate.ts と conductor の分業、forwarding loop）は実行モデルを参照。

package manager と DRY の境界

package manager は、ツール非依存の定義を Kiro・Claude Code・Cursor・GitHub Copilot 向けの構成物（subagent・skill）へ投影する。DRY を保つため、各 stage 定義は正規の 1 ファイルで維持する。ツール固有実装は内容を物理コピーせず、ファイル名参照で指す。

共有定義は「ツール間の最小公倍数」に切り詰めない。だから覆う範囲と覆わない範囲に明示的な境界を引く。覆うのは stage 構造、区画 1 と区画 2 の契約、orchestrator ヒント、stage 横断の事後条件ライブラリである。覆わないのはツール固有の機能であり、Claude Code の skill スコープ hook、Cursor Composer の複数ファイル編集、Copilot Workspace の PR ネイティブなループ、Kiro の spec-kit の差分提示がその例になる。ネイティブ機能を上に重ねる責任は各ツールの emitter が負う。こうして可搬性とツール固有の利点が両立する。v2 の実際の packaging（buildTree・manifest 契約・emit()）はリポジトリ構成を参照。

実装ガイドライン 8 項

実装が守る規律は 8 行に圧縮されている。v2 はこの 8 項をそのまま機構に落とした。次節の対応表で実体に接続する。

#ガイドライン内容
1決定論的ルーティングstage の順序とワークフロー遷移はオーケストレーション層が決める
2エージェントの専門化ドメイン判断は適切な専門家ペルソナに委譲する
3成果物のトレーサビリティ各 stage が consume / produce するものを宣言する
4人間の承認ブートストラップ以外の stage は明示的な承認を要する
5ツールが所有する状態状態と監査の遷移は機械的に処理する
6助言としての検証チェックは品質判断と監査可能性を支援する
7統制された学習新しいルールは意図的に受け入れる。静かに入れない
8隠れた委譲の禁止エージェントは再帰的にエージェントを生成しない。調整は conductor が行う

仕様 → v2 実装の対応

仕様の概念は v2 リポジトリでほぼ 1:1 の実体を持つ。概念から実装へ降りるときの索引に使える。

仕様の概念v2 での実体解説ページ
区画 1「What」（入出力の宣言）stage frontmatter の produces / consumes / requires_stage。パスはエンジンが解決実行モデル
区画 2（推論的検証）敵対的レビュアー 2 体（REFUTE 契約・balanced tier）。LLM 判定のみでは完了できず人間ゲートが残る設計も仕様どおりエージェントと検証
区画 2（計算的検証）センサー 5 種（決定論・現時点は advisory。ブロッキング化は roadmap 上の将来分）エージェントと検証
区画 3（実行時の学び）観察日誌 memory.md + §13 学習ループ（surface / persist、承認必須、RULE_LEARNED / SENSOR_PROPOSED）エージェントと検証
自己修正ループの停止条件reviewer_max_iterations（既定 2）と Bolt 失敗時の halt-and-ask（自律モードでも必ず停止）方法論モデル
orchestrator（5 機能）決定論エンジン aidlc-orchestrate.ts（routing・状態追跡・監査）+ conductor（実行品質）の分業実行モデル
Skills を合成単位に（原則 6）stage / scope ごとに生成される skill runners（aidlc-runner-gen）と composer による適応構成方法論モデル
package managerscripts/package.ts + harness manifest。正規定義 1 箇所・ツール別出力・ネイティブ機能は emitter が上乗せリポジトリ構成
拡張可能性（原則 8）plugin 機構（stages / sensors / agents の寄与）+ 5 層ルールの厳密加算リポジトリ構成
ガイドライン 8「隠れた委譲の禁止」全エージェント frontmatter の disallowedTools: Taskエージェントと検証
仕様と実装の距離 仕様の一部は到達目標として書かれている。Skills を第一級の合成単位にする再編（原則 6）、検証の自己停止範囲の拡大、センサーのブロッキング化がそれだ。いずれもリポジトリの roadmap（2.4.0 の Verifier 強化、2.5.0 の 3 ロールアンサンブル）で漸進中の領域にあたる。
