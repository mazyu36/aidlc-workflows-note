AIDLC-WORKFLOWS / SPEC

方法論仕様 — AI-DLC Workflows 2.0 Specification を図で読む

リポジトリ同梱の仕様書（PDF・6 ページ）は、v2 の設計判断の根拠になっている概念モデルの原典。核は 1 つの狙い — 機械検証可能な検証を広げるほど人間の介入を減らせる、という「自律への漸進」— と、それを支える 9 原則・三区画モデル・自己修正ループである。このページは 9 原則を原典の論拠と具体例まで開き、三区画モデルと自己修正ループを図解し、orchestrator の 5 機能と package manager の DRY 境界を補い、v2 実装との対応表で締める。

原典: assets/AI-DLC-Workflows-2.0-Specification.pdf

仕様の位置づけ — v1 の方法論を保ち、ワークフロー層を作り直す

仕様の宣言はこう始まる: v1 は「人間を輪に入れた stage 列として SDLC を回す」価値を実証した。v2 は方法論を保ったまま、ワークフロー層を再構築して自律的なソフトウェアデリバリーへ漸進する — 機械検証可能な検証が広がるほど、人間の介入を減らす。再設計を駆動した力は 2 つ: 顧客が求めた「自分たちのデリバリーフローに合わせて組み替えられる、より細粒度で構成可能な部品」と、エージェント基盤の成熟（Skills、マルチエージェントランタイム、決定論的ライフサイクルフック、MCP）である。

仕様は 6 章構成: Context & Purpose、Principles（9 原則）、Structure（5 つの構成要素と Generate-Verify-Learn）、Orchestrator Definition（5 機能）、Package Manager、Implementation Guidelines（8 項）。以降の節がそれぞれを図解する。

9 つの原則 — 自律は「判断の蒸留」の漸進で達成する

9 原則は 1 本の論理でつながっている。人間の判断は機械実行可能な形に蒸留できる（P1）。ただし intent は曖昧に始まるのが自然だから、仮定せずに明確化する（P2）。事後条件があれば AI は停止条件付きで自己修正できる（P3）。その事後条件を持つ器が三区画モデルで（P4）、この器はあらゆる SDLC ステージに適用できる（P5）。一撃圧縮は事後条件の爆発と探索の爆発で破綻するから、段階分解する（P6）。蒸留は一晩では終わらないので安全な増分で進め（P7）、拡張可能性を最初から設計し（P8）、実践からの学びで検証ルールを潤す（P9）。

2 つの「原則」を混同しない ここで扱う 9 原則は Specification PDF が定める v2 の設計思想である。概念ページに出てくる 7 Core Principles は、全エージェントが毎ステージ読む共有ナレッジ（ai-dlc-principles.md）の運用原則で、これとは別物。9 は「なぜこの設計にするか」、7 は「実行時に何を守るか」を述べる。
#原則主張の要点
1人間の判断は機械へ蒸留できる判断・検証・操舵に費やす人間の労力は、判断パターンの体系的な蒸留で削減できる。自律への前提条件
2すべての intent は曖昧に始まる（それで良い）AI は仮定せず明確化質問で曖昧性を解消してから解く。欠陥ではなく自然な初期条件として受け入れる
3Safety Net 付きの自己修正ソルバーAI が改変できないプログラムで検査可能な事後条件 + 扱いやすい成功基準 + 安価な反復、の 3 条件で収束する。停止条件（反復上限 / トークン予算）に達したら人間へエスカレーション
4三区画モデルstage を What（入出力）/ How Do We Know It's Right（事後条件）/ What Did We Learn（実行時の学び）の 3 区画で宣言する
5あらゆる SDLC ステージが同じ器に収まる実装系だけでなく、要件・設計・デプロイ・監視も「入力 → 出力の変換 + 明示的な事後条件」で記述できる
6一撃圧縮ではなく段階分解「このアプリを作って」1 発は事後条件の爆発と組合せ探索の爆発で破綻する。細粒度の部品 = Skills を合成単位に、stage / phase は柔らかい編成概念にする
7ビッグバンではなく安全な増分での自律化手持ちの規約から始め、guardrail を漸進的に事後条件へ蒸留（hydration）し、安全な増分の幅を広げる
8拡張可能性は基礎制約追加（additive）・置換（replacement）・合成（composability）の 3 形態を、ベンダー基準と同じ構文・同じ保証で顧客に開く
9実践からの学習（Compound Engineering）人間の修正・やり直し・escape-hatch 受諾を候補ルール化し、人間の承認を経て有効ルールへ昇格する。手作業の執筆だけに頼らない hydration 経路

以下は 9 原則それぞれの論拠と、原典が挙げる具体例である。表が要点の索引、ここが原典の散文に対応する。

原則 1 — 人間の判断は機械へ蒸留できる

判断・検証・操舵に費やす人間の労力の相当部分は、判断パターンを機械実行可能な構成物へ体系的に蒸留することで削減できる。これは自律的なソフトウェア開発へ近づくための前提条件であり、かつ推進力でもある。仕様は限界も率直に述べる — human-in-the-loop を完全に除去できるかについてはまだ合意に至っていない。ただし「すべての stage で必要な人間の労力を下げ続ける」ことは必須事項として一致している。現状の AI-DLC はあらゆる stage で人間に強く依存するが、それを恒久的な前提ではなく最適化すべき初期条件として扱い、自動化層を時間をかけて hydration していく。

原則 2 — すべての intent は曖昧に始まる（それで良い）

あらゆる SDLC のビジネス intent は、仕様記述能力の限界・本人も気づかない unknown-unknowns・自然言語固有の曖昧性から、ある程度曖昧に始まる。だから AI は仮定を置かず、明確化質問で context を集め、解き始める前に可能な限り intent を明確化する。「売上ダッシュボードを作って」という依頼には、どの指標を・どの期間で・誰に向けて・何のために、という多数の言われざる前提が潜む。これを欠陥ではなく自然な初期条件として受け入れ、human-in-the-loop で AI が確認と人間の判断取得を行う。intent statement を事前に丁寧に整えておくほど、この stage は効率化できる。

原則 3 — Safety Net 付きの自己修正ソルバー

入力・期待される出力・健全かつ完全な事後条件が与えられれば、AI は事後条件に照らして検証と修正を反復し、いずれ解へ収束できる。この収束は 3 つの構造的性質に依存する: (1) 事後条件が、AI が改変できないプログラムで検査可能であること、(2) 成功基準が扱いやすい（tractable）こと、(3) 反復が十分に安価で多数の候補を試せること。これらが成り立つ stage（Build & Test、インフラのプロビジョニングなど）は収束まで自己修正できる。検証が機械的でない stage（要件分析、設計批評、UI モックアップなど）は、事後条件が健全かつ完全に hydration されるまで人間の検証を保持する。ただし現実には、あらゆる問題が妥当な時間・トークン予算で解けるわけではない。そこで自己修正ループには必ず停止条件（反復回数の上限またはトークン予算）を設け、収束できなければ無限に続けず人間へエスカレーションする（参考: 「AI Agents as Universal Task Solvers」、Karpathy の autoresearch）。

原則 4 — 三区画モデル

原則 3 を運用可能にするのが三区画モデルである。stage の仕事を、生成仕様（区画 1）・自己検証仕様（区画 2）・学習仕様（区画 3）の 3 区画で表す。区画 1「What」は入力と出力を定義する — 例えば User Stories を入力に取り Domain Model を出力する、という宣言である。品質が依存する中間成果物（例: Bounded Contexts Design に至る過程での event・aggregate・bounded context 境界の識別）は、命令的な指示を埋め込むのではなく明示的な追加出力として名指す。これで区画 1 は宣言的なまま、下流の品質が要する成果物の生成を保証できる。区画 2「How Do We Know It's Right」は事後条件 — 正しい出力が満たすべき規則・制約・品質チェック — を定義する。区画 3「What Did We Learn」は実行時学習の捕捉を定義する: どの観測シグナルが候補ルール・exemplar・事後条件になり、区画 2 や共有 guardrail ライブラリへどう昇格提案されるか。事後条件が無ければ AI は自己修正できず、入出力定義が無ければ何を解いているか分からない。事後条件の健全性・完全性は当初は揃わないため、初期はより頻繁に人間の検証へエスカレーションし（現行 AI-DLC がそうであるように）、区画 2 を漸進的に hydration して最終目標へ近づく。例えばダッシュボード生成では当初は配色を人間に確認するが、組織の UI 標準とその逸脱を検査する事後条件を与えれば自律度が上がる。

原則 5 — あらゆる SDLC ステージが同じ構成に収まる

三区画構成は十分に一般的で、AI-DLC（あるいは任意のソフトウェア開発プロセス）のあらゆる stage を記述できる。コーディングやテストのような実装中心の stage に限らず、要件明確化・アーキテクチャ設計・デプロイ・監視などにも等しく適用できる。stage が創造的であれ分析的であれ機械的であれ、「定義された入力から期待される出力への変換を、明示的な事後条件で統制する」形に落とせる。（原典の見出しは "Two-Compartment Construct" だが、本文は three-compartment を指しており、ここでは三区画で統一する。）

原則 6 — 一撃圧縮ではなく段階分解

全 stage を単一ショットのプロセス（intent から即デプロイ済みコードへ）に圧縮するのは実際的でないと考える。理由は 2 つ:

  1. 事後条件の爆発 — 機能正しさ・コード品質・セキュリティ・コンプライアンス・性能・アクセシビリティ等をすべて一度に検証しようとすると、検証基準が過度に複雑で相互依存的になり、単一 stage での事後条件の定義・管理は仕様の悪夢になる。
  2. 組合せ探索の爆発 — すべての制約を同時に課すと、AI は膨大な解空間を探索せねばならず、長時間・非停止になりうるループを生む。まさに原則 3 の停止条件が防ごうとする暴走である。

加えて、この 1 年の顧客からの学びとして、規範的すぎる stage 定義は意見が強すぎて導入摩擦を生んだ。例えば AI-DLC 1.0 は Build & Test を 1 stage とするが、ほぼすべての顧客ではレビュー・ビルド・機能テスト・セキュリティテスト等の複数活動にまたがる。UI モックアップを User Stories と並行して作る顧客もいれば、Design stage へ遅らせる顧客もいる。ゆえに、顧客が自由に合成できる、より細粒度の ai-native な構成単位が要る。それが Skills である。Skills は、データベース設計・コードレビュー・セキュリティ分析など、従来は人間が提供してきた個別の能力/専門性を表す単位だ。その ai-native 表現（agentskills.io の仕様）は、指示・ツール・参照などを人間の実務者になぞらえてモデル化する。Skills を合成単位とし、stage / phase はより柔らかい編成概念とする。Skills のライブラリは原則 4 の三区画モデルで設計する。

原則 7 — ビッグバンでなく安全な増分での自律化

顧客は一夜で完全な自律デリバリーへ到達できない。現実の組織は、guardrail・no-go-zone 規則・コンプライアンス要件・セキュリティポリシー・ドメイン固有制約という膨大な蓄積を抱え、それらを機械実行可能な構成物へ蒸留してからでないと AI は自律的に動けない。この蒸留（健全性・完全性）は本質的に漸進的で、時間・組織的合意・反復的な洗練を要する。規制の厳しい大企業（社内コード標準・セキュリティレビューゲート・アーキテクチャ統制方針）を考えれば、それらは文書・暗黙知・レビューチェックリスト・人間の判断に符号化されており、区画 2 の事後条件へ一度に翻訳しきれる顧客はいない。AI-DLC 2.0 はこれを阻害要因ではなく想定される導入経路として受け入れる:

  1. 手持ちから始める — すでに知っていて符号化できる事後条件（コード標準・命名規約・基本的なセキュリティ規則）を定義し、その境界内で AI は自律動作し、それ以外は人間へエスカレーションする。
  2. 漸進的に hydration する — 時間をかけて guardrail・コンプライアンス・ドメイン規則を区画 2 定義へ蒸留する。追加のたびに AI が自律検証・自己修正できる範囲が広がる。
  3. 安全な増分を広げる — 事後条件ライブラリが成熟するにつれ、AI が一度に安全に実行できる範囲が拡大し、かつて各ステップで人間の判断を要した作業が複数 stage を跨いで自律進行できるようになる。

原則 8 — 拡張可能性

すべての顧客の guardrail・コンプライアンス義務・ドメイン固有ワークフロー・組織標準を先回りで予期することはできない。ゆえに拡張可能性は後付けの便利機能ではなく基礎的な設計制約でなければならない。顧客はベンダー提供のベースラインと同じ構成物・同じ保証で AI-DLC ワークフローを拡張・改変・合成できる必要がある。拡張モデルは 3 つのシナリオを支える:

  1. 追加的拡張 — 既存の AWS ベースライン定義の上に、自前の補足規則と事後条件を重ねる。
  2. 置換的拡張 — 要件がベースラインと乖離する箇所で特定の規則を置換し、以後その stage 定義の所有権を引き取る。
  3. 合成可能性 — 同じ三区画構成で著述したまったく新しい stage を導入し、AI がそれをワークフローへ賢く縫い込む。

原則 9 — 実践からの学習（Compound Engineering）

Skills の定義は、著述時だけでなく使用されるにつれて改善すべきである。各 Skill は生成仕様・検証仕様と並べて、実行時の相互作用（人間の修正・再実行・escape-hatch の受諾）から何を学ぶか、そしてそれらの観測がどう区画 2 ライブラリや共有 guardrail ライブラリへの候補追加になるかを宣言する。この層が無ければ、原則 7 の漸進的 hydration は手作業の著述だけに依存して導入が遅れる。今日、人間が AI の出力を修正しても、その修正は一度適用されて忘れられるのが常である。原則 9 の下では、あらゆる修正が学習候補になる。ユーザーが生成された要件文書の特定セクションを一貫して書き直すなら、その stage はそのパターンを捉える新しい事後条件を提案できる。ユーザーが特定の設計判断を繰り返し覆すなら、その stage は guardrail を提案できる。提案は有効ルール集合へ昇格される前に人間へ承認を求める。こうして実践そのものが検証ライブラリの hydration 源になる。

三区画モデルと自己修正ループ — 仕様の心臓部

実行モデルの核は「三区画で宣言された stage を、停止条件付きの自己修正ループで解く」こと。区画 2 の事後条件が無ければ AI は自己修正のしようがなく、区画 1 の入出力が無ければ何を解いているか分からない — 仕様はこの 2 文で器の必然性を説明する。区画 3 が学びの捕捉を担い、承認を経て区画 2 を太らせる（hydration）。ループが回るほど検証は濃くなり、人間の出番が減っていく。

区画 2 の検証は 2 形態に分かれ、性質がまったく違う。推論的検証（LLM 指示）は合否で切れない品質ヒューリスティクス（コードレビュー規範の大半）に向くが、生成者と同じモデルが自然言語の検査を判定すると「文言は満たすが意図を外す」危険がある。だから LLM 判定の事後条件しか持たない stage は自己停止せず、必ず人間の検証に出す。計算的検証（実行可能物）は曖昧さゼロで強制すべき規則 — 「本番の CloudFormation スタックを削除するコードパスを許さない」「認証なしの API エンドポイントを公開しない」といった no-go-zone — に使い、決定論的に判定する。顧客が検証ルールを実行可能物へ蒸留するほど（原則 7）、人間の介入なしに自己停止できる stage の割合が増える。

構造 — 5 つの構成要素と DRY

仕様が定める構造は 5 つ: Persona-Agents・Stages・Knowledge の 3 ライブラリ、それらを適応的ワークフローへ合成する orchestrator、そしてツール別の構成物へ投影する package manager。設計原則は DRY・関心の分離・「各ツールのネイティブ機能を最大限使う（最小公倍数に落とさない）」の 3 つ。

orchestrator の 5 機能

orchestrator は Skills のワークフローを合成・順序付け・監視・適応させ、一貫した end-to-end の開発フローにまとめる。各 stage が宣言するメタデータ — 区画 1 の入出力（形式・依存の期待を含む）、stage の目的、stage 定義が持つ orchestrator ヒント（順序制約・条件付きトリガ・エスカレーション方針）— を用いて組み立て方を決める。担う機能は 5 つ:

  1. ゴールの所有 — end-to-end の目的を所有し、宣言された成果の提供に責任を負う。ゴール追跡を個々の stage へ委譲せず、マクロな視点を保ち、全 stage の集計出力が元の intent を満たすことを保証する。
  2. ワークフロー構成 — 離散的な stage を適応的ワークフローへ組み上げる。構成判断は intent の性質（greenfield とバグ修正/リファクタで異なる並び）・利用可能な context（包括的な文書が既にあれば stage を省略/簡略化）・stage 出力と実行時シグナル・orchestrator ヒント付きの顧客作成 stage（原則 8）に左右される。固定パイプラインには従わず、順序付き構成の plan を保つが、それは実行中も可変である。
  3. ルーティング・可観測性・制御 — ワークフローの運用制御面。先行出力や元の intent から正しい入力を引いて stage をトリガし、実行状態（走った stage・結果・成果物）を追跡し、原則 3 の停止条件を強制する。stage が収束できないときはエスカレーション（一時停止・人間への表面化・解決後の再開）を管理し、どの stage をなぜどの順で起動したかの完全な監査証跡を保つ。
  4. 抽象化境界 — 各 stage をブラックボックスとして扱い、内部動作に干渉せず、完了時に宣言された事後条件の充足のみを検証する。この分離がモジュール性を保ち、stage の独立進化を許す。
  5. stage 横断の不変条件 — すべての事後条件が単一 stage に属するわけではない。命名規約・セキュリティポリシー・文書標準などワークフロー全体にまたがる不変条件を、適切なチェックポイントで評価し、どの stage 単独の責任でもないグローバル制約として強制する。

ここまでは仕様の抽象定義である。v2 での実体（決定論エンジン aidlc-orchestrate.ts と conductor の分業、forwarding loop）は実行の仕組みを参照。

package manager と DRY の境界

package manager は、ツール非依存の stage / orchestrator 定義を、Kiro・Claude Code・Cursor・GitHub Copilot などのツール固有構成物（subagent・skill 等）へパッケージ化する。DRY を保つため、各 stage 定義は正規の 1 ファイルで維持し、ツール固有実装はその内容を物理コピーせずファイル名参照で指す。ただし共有定義を「ツール間の最小公倍数」へ切り詰めないよう、共有が覆う範囲と覆わない範囲に明示的な境界を引く。共有定義が覆うのは stage 構造・区画 1 と区画 2 の契約・orchestrator ヒント・stage 横断の事後条件ライブラリである。覆わないのはツール固有の機能 — Claude Code の skill スコープ hook、Cursor Composer の複数ファイル編集セマンティクス、Copilot Workspace の PR ネイティブなループ、Kiro の spec-kit の差分提示など。各ツールの emitter が自プラットフォームのネイティブ機能を共有定義の上に重ねる責任を負い、生成物が各ツールの独自性を活かす。こうして共有定義は、ツールネイティブの利点を消さずに可搬性を保つ。v2 での実際の packaging（buildTree・manifest 契約・emit()）はつくりを参照。

実装ガイドライン 8 項

仕様の最終章は、実装が守るべき規律を 8 行に圧縮している。v2 実装はこの 8 項をそのまま機構化しており、次節の対応表で実体に接続する。

#ガイドライン内容
1決定論的ルーティングstage の順序とワークフロー遷移はオーケストレーション層が決める
2エージェントの専門化ドメイン判断は適切な専門家ペルソナに委譲する
3成果物のトレーサビリティ各 stage が consume / produce するものを宣言する
4人間の承認ブートストラップ以外の stage は明示的な承認を要する
5ツールが所有する状態状態と監査の遷移は機械的に処理する
6助言としての検証チェックは品質判断と監査可能性を支援する
7統制された学習新しいルールは意図的に受け入れる。静かに入れない
8隠れた委譲の禁止エージェントは再帰的にエージェントを生成しない。調整は conductor が行う
