エージェントと検証　小さなモブと 4 層の防衛線

エージェントは 14 体で、11 の広域ドメイン専門家に敵対的レビュアー 2 体とコンポーザー 1 体を加えた構成である。設計原則は「30 の狭い専門家ではなく、3〜5 人のモブを模した広いエージェント」に置く。品質は人間の承認ゲート 1 枚に頼らない。LLM による敵対的レビュアー、決定論で助言するセンサー、修正を永続化する学習ループが層を成す。

14 エージェント　Small Mob, Broad Agents

全員が共通の frontmatter 規律を持つ。1 つは Task ツールの禁止で、サブエージェントの再帰生成を封じる。もう 1 つは model 名を書かず tier（judgment / balanced / templated）を宣言することである。tier のパック時投影はリポジトリ構成を参照。

ナレッジシステム　6 段階のロード順

各プロデューサーエージェントは起動時に自分で知識を積む。順序は固定で、フレームワークの正からチームの上書きへ向かう。同梱のナレッジは 59 ファイルある。

  1. アクティブ space の memory/（org / team / project のルール）を読む。
  2. 共有ナレッジ aidlc-shared/（原則、検証、brownfield 安全策）を読む。
  3. エージェント別ナレッジを読む。developer なら code-generation-guide や api-design-guide にあたる。
  4. チーム側の共有ナレッジとエージェント別ナレッジを、存在すれば読む。最後に現在ステージの consumes 契約が指す前段成果物を読む。

ルールの適用対象は実行時に解決しない。compile が org → team → project → phase → stage の 5 層を厳密加算で解決する。上書きはせず、すべて足す。結果は各ステージノードの rules_in_context に焼き込まれる。ただし conductor へ渡すのはパスの一覧ではなく本文である。ステージ入場時、エンジンは run-stage の前に load-steering directive を順に返し、実質的な中身を持つルールファイルを分割して届ける。中身が空のテンプレートは落ちる。サイズ超過時にパス渡しへ退避する経路はない。

参照: core/knowledge/（59 ファイル） rules-reading.md（5 層解決の仕様） aidlc-developer-agent.md（Knowledge Loading 節の例）

レビュアーの敵対的契約　REFUTE から始める

レビュアー 2 体は成果物を作らない。ステージが reviewer を宣言していると、ゲート前に敵対的レビューが挟まる。指示は「この成果物を反証せよ」で、READY は探し尽くして到達できなかったときの結論であり、出発点ではない。NOT-READY ならリード単独が修正し、再レビューへ入る（既定で最大 2 往復）。エンジンは新しい REVIEW_COMPLETED の領収書が監査に載るまで、ステージ完了を拒む。レビュアーを宣言するステージは 12 ある。ワークフロー最初のステージ 1.1 intent-capture もその 1 つで、product-lead が出典の裏づけを専門に反証する。

architecture-reviewer には読み取り境界もある。担当 Unit の外、つまり他 Unit の construction/ ディレクトリはどのツールでも読めない。この境界は約束ではなく、PreToolUse フック（aidlc-reviewer-scope.ts）が exit 2 で機械的に拒否する。

レビュアーのチェックリストは実行時に読ませない。レビュアーは常に dispatch されるので、確実に届く経路は定義本文だけである。そこでパッケージャがビルド時に core/knowledge/<agent>/ の中身を各レビュアーの .md 本文へ吸収する。手書きの正はナレッジファイル側に残り、吸収後の本文は dist と同じ生成物になる。対象レビュアーはステージ frontmatter の reviewer: 行から導出するので、新しいレビュアーを宣言するステージが増えれば自動で追随する。

参照: aidlc-architecture-reviewer-agent.md core/hooks/aidlc-reviewer-scope.ts scripts/agent-knowledge.ts（ビルド時の吸収）

センサー　決定論の第二意見（助言のみ）

センサーは「LLM の自己申告を信じない」ための決定論チェックである。成果物への Write/Edit のたびに PostToolUse フックが発火する。現在ステージに解決済みの sensors_applicable から、glob（matches）に合うものだけを走らせる。結果は SENSOR_PASSED / SENSOR_FAILED / SENSOR_BUDGET_OVERRIDE として監査に記録される。v2 の現時点では全センサーが advisory で、失敗してもワークフローは止まらない。失敗の詳細は record dir の .aidlc-sensors/ に落ちる。ツール不在（exit 127）や JSON 破損は失敗ではなく PASSED 扱いになる。検査基盤の不備でユーザーを煩わせないための設計である。

センサー対象（matches）検査内容タイムアウト
linter**/*.{ts,js}eslint（error 0 で合格。warning は失敗にしない）30 秒
type-check**/*.{ts,tsx}tsc の型検査60 秒
required-sections成果物 .md必須 H2 見出し（unit-of-work-dependency.md では DAG の整形・非循環も検査）5 秒
upstream-coverage成果物 .md上流成果物の言及カバレッジ5 秒
claim-sources成果物 .md1.1 intent-capture の主張が出典タグを持ち、questions ファイルの回答に解決するか5 秒

5 番目の claim-sources は出典の追跡を担う。1.1 intent-capture の成果物では、段落、箇条書き、表の各行が出典タグを持つことを要求する。タグは [desc] / [scope] / [Q<n>] / [memory:<id>] / [assumption] の 5 種である。センサーが見るのはタグの形と解決先だけになる。[Q3] なら同階層の intent-capture-questions.md に記入済み回答があるかを確かめる。[desc] と [scope] は aidlc-state.md の記述と完全一致を求める。引用元が主張を本当に支持するかの判断は、ステージの敵対的レビュアーが持つ。残した assumption は ## Assumption Confirmation での人間の明示承認がないと通らない。

Construction swarm　並列 worktree と権威ゲート

人間が自律モードを許可した Construction では、バッチ内の Unit を並列に建てられる。責務は 3 分割される。conductor（LLM）が fan-out と再試行ループを持ち、決定論ツール aidlc-swarm.ts が収束判定、改竄ガード、直列マージ、監査を持つ。人間は自律の許可と失敗時の引き取りを持つ。

判定の要は「worker の自己申告を信じない」ことである。check は検査コマンドの exit 0 だけを正とする。finalize は conductor が完了したと主張した Unit を全数再検証する（lying-conductor guard）。レビュアー宣言ステージでは REVIEW_COMPLETED の領収書も確認する。そのうえで合格 Unit だけを 1 つずつ直列にマージする。

参照: core/tools/aidlc-bolt.ts（Bolt のライフサイクル） core/tools/aidlc-worktree.ts（worktree 原始操作 5 種） docs/harness-engineering/08-construction-and-swarm.md

学習ループ　修正を永続ルールに変える

学習ループは「同じ指摘を二度させない」ための仕組みである。ステージ実行中の観察は record dir の memory.md（観察日誌）に溜まる。承認ゲート直前の §13 儀式で、決定論ツールが日誌の非空行をそのまま候補として提示する。ユーザーが残すものを確定すると、practice として space の memory/project.md に追記される。team.md へは 1 クリックで昇格でき、org への昇格経路はない。着地前には org.md との節単位の矛盾チェックが走る。矛盾があればゲートが止まり、revise / skip / 上申を選ばせる。

学びが将来に効く経路は 3 つある。compile が次回の rules_in_context に焼き込む、各エージェントが起動時に memory/ を再読する、SessionStart フックが再開時に文脈を注入する。学習ループの中心にあるのは人間の確認である。観察の採否も、org との矛盾の裁定も、ツールと LLM ではなくユーザーが決める。
