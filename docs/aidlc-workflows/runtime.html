AIDLC-WORKFLOWS / RUNTIME

実行モデル　決定論エンジンと forwarding loop

セッションは 1 つの単純なループで動く。決定論エンジン（aidlc-orchestrate.ts）が「次の一手」を JSON directive で返し、conductor（LLM）がその一手だけを実行して report で結果を返す。routing はエンジン、実行品質は conductor、状態を書けるのは aidlc-state.ts だけ、承認できるのは人間だけ。この役割の壁をツールとフックが強制する。

forwarding loop　1 ステージが流れる様子

ユーザーが /aidlc を打つと、conductor は「next → 一手を実行 → report → 繰り返し」のループに入る。手順はスキル定義が規定する。エンジンの next は状態ファイルとコンパイル済みステージグラフを読み、型付き directive をちょうど 1 つ stdout に返す。種類は run-stage / invoke-swarm / ask / print / error / done / parked の 7 つで、この間なにも書き換えない。run-stage directive には、ルール、ペルソナ、ステージファイル、入力成果物のパスが解決済みで入る。最初の 1 通だけ conductor.md の全文（conductor_persona）が焼き込まれる。

sequenceDiagram
  participant U as ユーザー
  participant H as Hooks
  participant C as Conductor（LLM）
  participant E as Engine（orchestrate）
  participant S as State（aidlc-state.ts)
  U->>C: /aidlc [引数]
  H->>H: SessionStart: 文脈注入 + SESSION_STARTED
  C->>E: next $ARGUMENTS
  E->>E: nextInScopeStage() で次ステージ決定
  E-->>C: run-stage directive（JSON・読み取り専用）
  C->>C: rules → persona → stage file → consumes を読む
  C->>C: ステージ本体を実行し produces を書く
  H->>H: PostToolUse: ARTIFACT_* / SENSOR_* を監査へ
  C->>E: report --result awaiting-approval
  E->>S: gate-start（[-] を [?] へ）
  C-->>U: 承認ゲート提示（HARD STOP）
  U->>C: Approve
  H->>H: HUMAN_TURN を監査へ
  C->>E: report --result approved
  E->>S: approve（[?] を [x] へ + auto-advance）
  E-->>C: done（次の next を実行せよ）
  C->>E: next（ループ継続）

ループの実体はスキル文書の 4 行の擬似コードで、エンジンと conductor の分業宣言は conductor.md の冒頭 5 行にある。

ステージプロトコル　32 ステージが従う共通契約

各ステージは 1 枚の .md ファイルである。YAML frontmatter は 14 の authored フィールドを持つ。slug / phase / lead_agent / mode / produces / consumes / requires_stage がその一部である。本文は Steps / Sensors / Learn の順序が固定される。成果物のパスをステージファイルにハードコードすることは禁じられ、エンジンが directive 発行時に record dir の実パスへ解決する。全ステージの振る舞いは 1,147 行の stage-protocol.md が統べ、その中核が承認ゲートの HARD STOP 規則になる。

参照: core/aidlc-common/protocols/stage-definition.md（frontmatter 仕様） stages/inception/user-stories.md（mob 実行の例）

次ステージの決定　グラフ × スコープ × 状態上書き

routing の中心はただ 1 つのループである。コンパイル済みグラフを現在位置から前方へ歩き、完了、スキップ済みを飛ばし、スコープ行列で最初の EXECUTE ステージを返す。行列の判定では state 側の EXECUTE/SKIP 上書きが優先される。返すものがなければワークフロー完了になる。

状態機械と監査　書けるのは 1 つのツールだけ

進捗の正は record dir 直下の aidlc-state.md である。各ステージは 6 状態のチェックボックスで表される。遷移を実行できるのは aidlc-state.ts だけで、動詞は advance / gate-start / approve / reject / revise / skip になる。conductor が状態ファイルを直接書き換えようとすると、PreToolUse フックが exit 2 で拒否する。全遷移は「監査を先に書き、状態を後に書く」順序を守り、ディレクトリ mutex（mkdir ロック、50 回 × 100ms リトライ）に包まれる。

監査はイベント 74 種、19 カテゴリの追記専用ログである。書き込み先は audit/<host>-<clone>.md というクローンごとのシャードになる。読む側が全シャードを glob してタイムスタンプでマージするので、並列 worktree からの追記でも git コンフリクトが起きない。実行時に生成されるワークスペースの全体像は次のとおり。

aidlc/ # ワークスペース（git コミット対象） ├── active-space # カーソル（gitignore・ユーザー毎） └── spaces/<space>/ ├── memory/ # ルール層: org / team / project / phases/* ├── knowledge/ codekb/<repo>/ # チームナレッジ / 逆解析の成果（9 成果物） └── intents/ ├── intents.json # 登録簿 {uuid, slug, scope, status} └── <YYMMDD>-<label>/ # record dir（intent 1 件の全記録） ├── aidlc-state.md # 進捗の正（このセクションの主役） ├── audit/<host>-<clone>.md # 追記専用の監査シャード ├── <phase>/<stage>/ # ステージ成果物 + memory.md + questions ├── .aidlc-sensors/ # センサー失敗の詳細ファイル └── runtime-graph.json # データプレーンの読み取りモデル（gitignore）

フック 13 本　ハーネスイベントへの接続

Claude Code では settings.json が 8 イベント種に 13 本のフックを束線する。10 本は記録専用で流れを止めない。流れを変えるのは 3 本だけである。state-transition-guard が状態ファイルへの直接書き込みを拒否し、reviewer-scope がレビュー中の越境読み取りを拒否する。3 本目の Stop フックは、ゲート、park、done 以外でターンを終えられなくする。Stop フックは停止のたびに orchestrate next を裏で回し、途中なら decision:block で directive を注入してループを続けさせる。forwarding loop の「繰り返し」は、この Stop フックが機械的に強制している。

非 Claude ハーネスは同じ 13 本をバイト同一のまま使う。authored な adapter 1 枚がネイティブイベントを Claude 形式の stdin へ正規化し、子プロセスとして実行する。写像はハーネスごとに違う。Codex の apply_patch はファイルごとの Write/Edit に展開され、Kiro の todo_list は TaskUpdate に対応する。opencode はフックレジストリ自体を持たないので、プラグインのハンドラ関数として同じ変換を行う。exit 2 と decision:block という流れを変えるチャネルも、各ハーネスのネイティブなブロック手段へ透過的に転送される。

CLI 面　1 つのディスパッチャと 20 のツール

aidlc.ts（1,134 行）はルーティング専用のシムである。受ける形は 2 系統ある。aidlc <verb> は 13 のトップレベル動詞を取る（next / report / park / compose / status / doctor / init ほか）。aidlc <noun> <verb> は 20 の名詞を取る（state / audit / graph / runtime / sensor / swarm / bolt / worktree / jump / learnings ほか）。いずれも 20 の兄弟ツールへ委譲する。エンジン中枢の orchestrate が公開するのは next / report / park の 3 動詞だけで、state は 24 動詞を持つ。「決める者は書かず、書く者は決めない」の分離が、CLI の面にもそのまま現れている。

参照: core/tools/aidlc.ts:53-74（TOOLS 対応表） docs/guide/12-cli-commands.md

再開・ジャンプ・復旧

中断への備えは 4 系統ある。

  1. 再開。SessionStart フックが状態の生きたフィールドと forwarding loop の規律を additionalContext として注入する。続いて Resume / Redo / Jump / Start Fresh のメニューを出す。
  2. ジャンプ。aidlc-jump.ts が 2 段で状態を書き換える。resolve が方向と影響範囲を計算し、execute が前方なら途中を [S] に、後方なら下流を [ ] に戻す。
  3. コンパクション。PreCompact フックが復旧ブレッドクラム .aidlc-recovery.md を書く。resume は監査末尾の SESSION_COMPACTED を見て継続確認を挟む。
  4. 中断。park がステージ境界でワークフローを綺麗に停止させ、/aidlc --resume が解除する。
